# The AVX-512 variant

This tree is `natural-lib` plus AVX-512 / IFMA kernels for the merged radix-4 passes of the
NTT.  Everything else -- the four-level DRAM/L3/L2/L1 schedule, the planner, the wrap
correction, the division drivers -- is shared with the scalar library; the schedule files
here are a copy of that tree's `sched-refactor` state.

## Kernels

`src/mul_ntt_avx512.s` adds two entry points with the same signature, the same two merged
layers and the same twiddle cursors as the scalar `nat_asmNtt2_radix4` /
`nat_asmINtt2_radix4`:

```c
void nat_asmNtt_zmm_radix4 (uint64_t D, uint64_t mod, uint64_t* Begin,
                            const uint64_t* RootO, const uint64_t* RootI, uint64_t* End);
void nat_asmINtt_zmm_radix4(uint64_t D, uint64_t mod, uint64_t* Begin,
                            const uint64_t* RootO, const uint64_t* RootI, uint64_t* End);
```

and a pair of single-layer kernels for the schedule's unpaired layer, one zmm per half of a
2N block (`N >= 8`), same layers and cursors as the scalar `nat_asmNtt2` / `nat_asmINtt2`:

```c
void nat_asmNtt_zmm_radix2 (uint64_t N, uint64_t mod, uint64_t* Begin,
                            const uint64_t* Root, uint64_t* End);
void nat_asmINtt_zmm_radix2(uint64_t N, uint64_t mod, uint64_t* Begin,
                            const uint64_t* Root, uint64_t* End);
```

Mind the argument counts: the radix-2 kernels take five arguments, so `End` arrives in `r8`
and `Root` in `rcx`; the radix-4 ones take six and read `End` from `r9`.  (The scalar
kernels split the same way; getting this wrong is a silent out-of-bounds walk, so the
per-`D`/per-`N` identity tests are the guard.)

One 4D macro-block holds four quarters `a/b/c/d` of D elements; the kernels keep one zmm per
quarter, so **D must be a multiple of 8** and the sequence is the one verified in
`verify/experiments/butterfly_r4_ifma.s`:

* twiddles are broadcast per block exactly as the scalar kernel reads them (uniform within a
  block): `RootO` supplies `(w, w')` for the distance-2D layer, `RootI` supplies `(w2, w2')`
  and `(w3, w3')` for the distance-D layer; `RootO` advances 16 bytes and `RootI` 32 per
  block, so the positional cursor rules are unchanged;
* the Shoup multiply is pure IFMA: `vpmadd52huq/luq` build `q = hi64(v*w')` and
  `lo64(q*m)`, exploiting the moduli's `m = a*2^56 + 1` shape, and a masked `+m` corrects
  the sign of `z`.  No `mulx`, no 128-bit scalar multiply.

## Why the finest level has a "tail"

The zmm kernel needs `D >= 8` (one zmm per quarter).  The two lowest layers of the last
level are `(3,2)` at `D = 4` and `(2,1)` at `D = 2`, so instead of writing a second kernel
for `D = 4` the plan peels the **fixed distance-2 pair** `(2,1)` off the finest level:

| level state | merged range | unpaired layer | tail |
|---|---|---|---|
| `k` even | `3 .. k-2` | none | `(2,1)` at `D = 2` |
| `k` odd | `3 .. k-2` | layer 3 at `D = 8` | `(2,1)` at `D = 2` |

The merged range then starts at layer 3, so every merged pass left has `D >= 8`, `D = 4`
never occurs, and the only sub-8 shape in the whole transform is the fixed tail, which
`ntt_fwd_level` / `ntt_inv_level` hand to the *scalar* radix-4 kernel (`D = 2`, layers 2
then 1 forward, 1 then 2 inverse).  The unpaired layer moves from layer 1 to layer 3 and, at
`D = 8`, is a plain cross-register radix-2 pass.

`ntt_level::tail` carries this in the plan; `ntt_sched_for` sets it on the last level
together with `lo = 3` (for `k >= 4`, i.e. whenever the finest level's `hi >= 2`).

Cut points are therefore clamped to `>= 4` (the smallest chunk that hosts the tail's
8-element block and the distance-8 layer 3).  The shipping 12/16/20 always give the finest
level a tail; a scan point small enough to crowd the levels near layer 1 (all of `l1 <= 7`)
can leave the finest level with `hi < 2`, in which case the pair `(2,1)` stays in the merged
range and the `D >= 8` dispatch simply runs it -- and any `(3,2)` pair at `D = 4` -- on the
scalar kernel.  That is correct, just not vectorised, and the plan test only insists on the
tail for the shipping cut points.

## Switching it off

`ntt_zmm_enable` selects the zmm kernels; `false` runs every pass scalar.  Its default is
`ntt_zmm_cpu_ok()`, i.e. it asks the CPU (`__builtin_cpu_supports` for AVX-512
F/BW/DQ/VL/IFMA), so the tree builds, runs and passes its suite on a machine without the ISA
-- CI included -- by falling back to the scalar path.  Setting the flag explicitly forces
either implementation; it is a verification switch, not a tuning knob.

## Build

The assembly is accepted by GAS without extra ISA flags, but the *hardware* must provide
AVX-512 F/BW/DQ/VL and IFMA.  The CMake target adds nothing to consumer flags: the vector
instructions live in their own translation unit and the public headers stay free of
intrinsics, so a consumer still only needs `-masm=intel` (propagated by the target).

## Verification

`tests/test_natural.cpp` keeps the whole scalar suite -- it drives the vector path for every
size above the NTT threshold and checks the results against the 128-bit reference and the
Toom-22 base case -- and adds:

* `t_sched_plan`: the plan invariants including the tail (only the finest level owns it, it
  starts at layer 3, it is present whenever `k >= 4`, and the levels plus the tail tile
  `1 .. k-2` exactly);
* `t_zmm_kernels`: one pass at a time -- radix-4 for every `D = 8 .. 2^(scale-2)` and
  radix-2 for every `N = 8 .. 2^(scale-1)`, both directions, all three moduli --
  **bit-identical** to the scalar kernels;
* `t_zmm_paths`: end to end, the whole engine with `ntt_zmm_enable` on and off must produce
  identical products and squares (sizes 896 .. 70000 limbs).

Mutation checks were run against this suite (not committed): corrupting one inner twiddle of
the forward zmm kernel fails the per-D check for all 12 `D`, the engine A/B for all 7 sizes
and the base-case oracle; disabling the tail fails the plan check for `k = 4 .. 24`; a wrong
tail cursor is caught by the base-case oracle (the engine A/B cannot see it, because the tail
is the same scalar code in both paths -- that is exactly what the oracle is for).

## What is still scalar, and why

The deciding question is not "does it need a 64x64->128 multiply" but "is one operand
*known*".  AVX-512 has no 64x64->128 instruction; emulating `hi64` costs about as much per
element as scalar `mulx` plus `imul`, so a block that needs a product of two live values is
not worth vectorising.  But a product with a precomputed constant (a twiddle, the modulus'
mu, a CRT constant, the inverse of the transform length) is exactly what the IFMA Shoup
sequence in `S56` already does, and a block with no multiply at all is a pure win.

* the **inverse D = 2 tail** -- the forward one is done; the inverse's inner layer multiplies
  the derived differences (`(a - b) + m`), so it needs fewer gathers than the forward scheme
  (one blend plus a 4-lane shift rather than two vpermt2q stages), and it is worth about
  another 2% of a product;
* `nat_asmNttMul` -- the pointwise product in the middle multiplies two *live* limbs: there
  is no reciprocal to Shoup with, and neither Barrett nor Montgomery avoids the true 128-bit
  product.  Left scalar on purpose; vectorising it would mean a 2x52-bit limb
  representation, which doubles the (already memory-bound) traffic.
* `load()` -- the fold's butterflies are multiply-free and every input limb is reduced mod p
  by `barrett_mod`, i.e. a multiply by the *constant* mu.  Vectorisable in principle, but
  the hollow twin below shows it is **memory-bound**: leave it alone.
* `intt_shr()` -- one multiply-free layer (the distance-N/2 one) plus a multiplication by
  the constant `2^-s` and the carry chain.  Arithmetic-bound, but small.
* `nat_asmCRT()` -- the per-coefficient CRT merge, again products with precomputed
  constants, but 4-8x above its memory floor: **the one remaining piece with a real
  payoff**.

Hollow twins (`perf_hollow.cpp`: identical address stream -- same loads, stores, loop
structure and tail memset -- with the modular arithmetic dropped, real and hollow
alternating in one process) put numbers on it.  hollow/real at 2^22 / 2^16 limbs:

| stage | hollow/real | verdict | ceiling if the arithmetic were free |
|---|---|---|---|
| `load()` | 0.97 / 0.90 | memory-bound | 0.1-0.3% of a product |
| `intt_shr()` | 0.65 / 0.28 | arithmetic-bound, small | 0.7-1.3% |
| `nat_asmCRT()` | 0.26 / 0.13 | arithmetic-bound | 2.5-3.7% |

`load()`'s reduction is almost entirely hidden behind its traffic (within 3-10% of a pure
copy), which is why its 3.5% share is not worth attacking.  In `intt_shr()` the constant
multiply is ~20-30% of the stage (a twin with the multiply dropped, the layer kept, measures
0.83 / 0.73).  The CRT merge is the outlier at 4-8x its floor, because it does two real
64x64->128 multiplies per coefficient.

Chasing the CRT's loads in scalar, the obvious win is to fold the loop-invariant constant
loads into the multiplies that consume them: of the five per coefficient, three can
(`imul`/`mulx` take a memory operand), two cannot (`mul`'s multiplicand is fixed to rax, and
m1 feeds two multiplies).  That change is bit-identical (`perf_crt.cpp` hashes the whole
output plus both carry words) and removes three instructions per coefficient -- and it
measures **neutral**: two identically-built binaries differ by 1-4% in the same session, and
the fold lands inside that.  The reason is the bottleneck.  The CRT is limited by the
multiplier ports (~six 64x64 multiplies per coefficient, spread over p1/p5), not by load
slots or the front end, so removing load *instructions* cannot help.  Only a vector CRT --
eight coefficients per multiply instruction -- attacks what is actually saturated, which is
why it remains the one piece of this variant still worth writing.

So the only worthwhile kernel left is the CRT merge: worth ~2.5-3.7% of a product, i.e.
1.57x -> about 1.63x end to end.  `nat_asmNttMul` stays scalar unless the number
representation changes.

## Performance status

End to end, same session, one pinned core, mains power, minimum over rotated rounds, powers
of two from 896 to 4 194 304 limbs (`perf_scalar_ab.cpp` against the scalar tree, plus
`perf_pow2_gmp.cpp` against GNU MP 6.3.0):

| build | geomean vs the scalar library (mul / sqr) | vs GMP, 2^16..2^22 limbs (mul / sqr) |
|---|---|---|
| radix-4 kernels only | 0.656 / 0.659 (1.52x) | 1.73..2.32x / 1.46..2.19x |
| + radix-2 unpaired pass | 0.636 / 0.639 (1.57x) | 1.73..2.32x / 1.51..2.19x |
| + packed D = 2 tail, forward | **0.604 / 0.616 (1.65x / 1.62x)** | 1.73..2.32x (unchanged) |

The unpaired radix-2 pass was worth ~3% (1.52x -> 1.57x), consistent with it being one layer
of the `k-2` scheduled ones.  The D = 2 tail is worth ~5% on the product and ~3.5% on the
square -- the square runs one forward transform to the product's two, and only the forward
tail kernel exists so far, which is exactly the 2:1 split the measurement shows.  Measured in
isolation the packed kernel beats the scalar tail pass by 1.7x at every chunk size
(`perf_tail.cpp`, v/s = 0.56..0.66 for T = 9..19).  The gain does not fade at the top of the range
(0.62 at 2^22), which matches the earlier `hollow / real = 0.52` measurement: the scalar
kernel sat about 2x above the pure-memory floor, so halving its arithmetic reaches down
towards it.  At 2^22 limbs (33.5 MB operands) the variant is 2.18x GMP for the product and
2.16x for the square; every row was compared limb by limb against GMP.

A stage-by-stage probe (`perf_stages.cpp`: 2x load + 2x ntt + NttMul + intt + save per
product) shows what is actually left.  (It was taken before the tail kernel; with the
forward tail vectorised, what remains is the inverse tail plus the pieces below.)  Of the scalar build's time at 2^22 limbs the shares
are **ntt 57%, intt 31%, NttMul 4.8%, load 3.5%, save 3.4%** (2^16 limbs: 55% / 30% / 6.4%
/ 3.2% / 4.8%), i.e. the transform itself is ~88% and is already vectorised.  The kernels
give 1.82x on `ntt`, 1.69x on `intt`; `load`, `NttMul` and `save` are untouched at 1.00x.

So `nat_asmNttMul` -- the one block that cannot be Shoup'd -- is only ~5% of a product, and
the two constant-multiplier pieces (`load()`, `save()`) are ~3.5% each; `intt_shr()` sits
inside the `intt` number.  The hollow twins above show that only the CRT merge has real headroom left.
